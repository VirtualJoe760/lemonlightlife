# Data model

Three collections. `subcontractors` is the searchable roster (renamed from
`crew` to match the product vocabulary — a subcontractor is either an
individual specialist or a day laborer available for hire). `searchlogs` and
`chatlogs` are append-only records for training / analysis.

## `subcontractors`

```
{
  _id             ObjectId
  name            string           // "Marcus Alvarez"
  gender          "male" | "female" // used to match headshot pool
  headshotUrl     string           // "/headshots/electrician-male-03.png"
  roles           [string]         // canonical role keys from shared/roles.js
                                    // e.g. ["electrician"] or ["carpenter", "framer"]
  specializations [Specialization] // see below — the real matching signal
  yearsExperience number           // 1–35
  city            string           // "Palm Desert"
  state           string           // "CA"
  county          string           // "Riverside"  (SoCal-only for this MVP)
  location        {                // GeoJSON Point — 2dsphere index
    type: "Point",
    coordinates: [lng, lat]
  }
  hourlyRate      number           // USD
  rating          number           // 1.0–5.0, one decimal
  certifications  [string]         // ["OSHA 30", "EPA Lead-Safe"]
  bookingStatus   enum             // "available" | "booked" | "unavailable"
  bio             string           // 1–2 sentence blurb (Atlas Search text field)
  createdAt       Date
  updatedAt       Date
}

type Specialization = {
  skill               string       // "vinyl flooring", "kitchen rewire" — from SKILL_POOL_BY_ROLE
  level               1 | 2 | 3 | 4 | 5    // 1=novice, 3=proficient, 5=expert (only ~15% of pool)
  yearsInSpecialty    number       // ≤ yearsExperience
}
```

### Why the switch from flat `skills[]` to `specializations[]`

A flooring subcontractor who's done 100 vinyl jobs and 3 hardwood jobs is
functionally different from one who's split evenly between the two. Flat
`skills[]` couldn't express that. `specializations[]` gives us three signals
per skill — the presence of the skill, the depth of practice, and the years
in specialty — which the ranker can weight explicitly.

At MVP the ranker uses `level` as the primary specialization signal; `years`
is available for future tuning and shown on the crew card.

### Level distribution (seeded)

| Level | Meaning | Share of specialization entries |
|---|---|---|
| 5 | Expert / go-to for this skill | 15% |
| 4 | Strong | 25% |
| 3 | Proficient | 35% |
| 2 | Familiar | 20% |
| 1 | Novice / helper | 5% |

Each subcontractor gets 3–6 specializations sampled from the skill pool for
their role(s). A crew member may have multiple level-5 specializations if
they're a true specialist, or a spread of lower levels if they're a
generalist.

### Why each other field

- **`roles` (array):** Real tradespeople carry multiple hats. Modeling as an
  array is the difference between "top match" and "best match."
- **`gender` + `headshotUrl`:** The seeder assigns a headshot deterministically
  from `client/public/headshots/manifest.json` by hashing `_id` and filtering
  by gender + primary role. Same person, same photo across sessions.
- **`county`:** Regional focus for this MVP is Southern California — LA,
  Orange, Riverside (incl. Coachella Valley), San Bernardino, San Diego,
  Imperial. `county` is denormalized so we can group results by area on the
  UI without another lookup.
- **`location` as GeoJSON Point:** required by `$geoNear`. Seeder jitters
  ±0.15° from city center so 10k markers don't stack.
- **`bio`:** Free-text field for BM25 to score fuzzy queries like "someone
  good with historic homes." Generated by the seeder from role +
  specializations + a Faker sentence for flavor.
- **`bookingStatus`:** Required by the brief. Enum (not free string) so we
  don't accidentally leak a fourth state.

### Indexes

| Index | Purpose |
|---|---|
| `2dsphere` on `location` | `$geoNear` in the ranker pipeline. |
| Atlas Search index on `roles`, `specializations.skill`, `certifications`, `bio` | BM25 ranking. |
| Plain `{ bookingStatus: 1 }` | Fast filter to `available`. |

### Atlas Search index (`subcontractor_default`)

```json
{
  "mappings": {
    "dynamic": false,
    "fields": {
      "roles":                    { "type": "string", "analyzer": "lucene.keyword" },
      "specializations":          { "type": "document",
                                     "fields": {
                                       "skill":  { "type": "string" },
                                       "level":  { "type": "number" }
                                     }
                                   },
      "certifications":           { "type": "string" },
      "bio":                      { "type": "string" }
    }
  }
}
```

`roles` uses the keyword analyzer because they're canonical vocabulary
values — we want exact matches ranked strongly, not partial word matches.
`specializations.skill` uses default text analysis for fuzzy skill matching.

## `searchlogs`

For direct `/api/search` calls (the brief-required endpoint).

```
{
  _id             ObjectId
  query           string           // raw sentence from the contractor
  parsedFilters   object           // JSON returned by the LLM parser
  resultIds       [ObjectId]       // subcontractor _ids in returned order
  topRationales   [string]         // per-match rationale strings
  latencyMs       number
  createdAt       Date
}
```

Written fire-and-forget. Failure never blocks the response.

## `chatlogs`

For `/api/chat` conversations (the UI's chat endpoint).

```
{
  _id             ObjectId
  sessionId       string           // client-generated UUID, groups a conversation
  messages        [Message]        // full transcript at time of write
  toolCalls       [ToolCallRecord] // every tool the assistant invoked, with args + result
  latencyMs       number           // end-to-end for this turn
  createdAt       Date
}

type Message = { role: "user" | "assistant" | "tool", content: string, toolCallId?: string }

type ToolCallRecord = {
  name:        string      // "search_subcontractors"
  args:        object      // parsed filters the LLM chose
  resultIds:   [ObjectId]
  latencyMs:   number      // ranker-only time
}
```

One `chatlogs` insert per assistant turn (not per user message). Also
fire-and-forget.

### Why keep both `searchlogs` and `chatlogs`

- `searchlogs` proves the brief-required `/api/search` endpoint works and
  gives us clean training data for the ranker (one sentence → one result set).
- `chatlogs` captures conversation context (follow-up refinements like
  "actually, only ones with EV charger experience") which is a richer signal
  for future model tuning but noisier for pure ranker training.
- Union of both is what we'd query for analytics.

## No indexes yet on the log collections

Volume is low. When we start querying them, add `{ createdAt: -1 }` and
possibly text on `query` / `messages.content`. For the trial project, no
indexes.
